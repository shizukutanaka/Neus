# SOCRATIC-AUDIT.md — 製品総括(長所 / 短所 / 改善点)

計測日: **2026-08-25** / 対象: v0.13.0(`main` = round 87 時点)
実測値: **1,803 tests / 107 files**、browser spec **185件**、監査ラウンド **6–87**(SPEC §10)

> **この文書の位置づけ**
> `FEATURE-AUDIT.md` は機能単位の台帳、`AUDIT-BRIEF.md` はレビュー担当への指示書。
> 本書は**製品レベルの総括**で、両者のどちらでもない。日付入りの記録なので数値を書いてよい
> (生きた文書に固定値を書かない規律 = round 45 の対象外。`docs-no-frozen-counts` の
> `LIVING_DOCS` は AUDIT-BRIEF と goal.md のみ)。
>
> **形式について**: この製品は v0.13 で「問い・反証条件・裁決」というソクラテス式探究を
> 実装している。**その認識論を製品自身に適用する**のが本書の形式である。各項目は
> 「問い → 実測による答え → 反問 → 判定」で書き、意見ではなく**実測**に紐づける。
> 反問を置くのは、肯定的な答えほど検算されないまま残るからである。

## 0. 判定の凡例

| 記号 | 意味 |
|---|---|
| **長所** | 実測で裏付けられた強み。反問にも耐えたもの |
| **短所** | 現に残っている弱み。回避策の有無を明記 |
| **改善点** | 次に打てる手。マスク5段階(疑う/削る/簡素化/加速/自動化)と**決定権者**を付す |

決定権者: **機械** = 即実行可 / **要ADR** = 設計判断が要る / **owner** = 人間にしかできない

## 1. 長所

### 1-1. 「サーバに送らない」が**主張ではなく検査対象**になっている

**問い**: ゼロ送信は本当か。どうやってそれを知るのか。

**実測**: BYOK 未設定でベンダへ一切通信しないことを spec で固定(round 69)。Worker は
リダイレクトの**ホップ毎に** SSRF 検証を通し(round 31)、サイズ上限は「中継しない」ためでなく
**「読まない」ために**逐次読みで効かせる(round 83)。`localStorage` 不使用は静的検査済み。

**反問**: *テストが通ることと、性質が成り立つことは同じか?* — **同じではない**。本セッションで
3回、テストが名前どおりの性質を検査していなかった(round 66 ミラー / 77 合成クラス名 /
83 streaming)。よって「検査済み」と言えるのは、**旧実装で赤くなることを確認した**ものに限る。
round 74 以降その手順を毎回踏んでいる。

**判定: 長所**(ただし範囲は round 74 以降に確認したものに限る)

### 1-2. 失敗を隠さない

**問い**: できないとき、この製品は何と言うか。

**実測**: 書けない(round 80: 「6件取得」と言いながら4件を捨てていたのを修正)、
開けない(round 81: `blocked` を拾わず空画面で無限待機していたのを修正)、
**残る保証がない**(round 82: `persisted()` が false でも何も言っていなかったのを STATS に表示)。

**反問**: *伝えれば十分か?* — 不十分。**次にできること**まで書いた(空き容量を空ける /
別タブを閉じる / インストールすると永続化される)。「何か問題が発生しました」は、直せるのが
利用者側にあるとき役に立たない。

**判定: 長所**

### 1-3. 検証の様式が確立している

**問い**: 何をもって「確かめた」と言っているのか。

**実測**: ミラーではなく**実ソースを評価**(`tests/helpers/from-source.mjs`)、
プラットフォーム依存の性質は**実ブラウザ**、性能は**実測してから**直す(round 78 の 21倍、
79 の 5倍)、そして**旧実装で赤くなることの確認**。round 74/75/78/80–83 で毎回実施。

**反問**: *その道具自身は検査されているか?* — **2回破綻していた**。`extractFunction` は
`async function` を見つけられず(round 72)、`extractConst` は配列リテラルを扱えなかった
(round 76)。どちらも「使おうとして初めて」判明。**道具の盲点は使用でしか出ない**。

**判定: 長所**(ただし道具自身の盲点は構造的に残る。反問を残す価値がある)

### 1-4. 性能が数値で押さえられている

**実測**: Lighthouse 相当 **99**(Slow 4G + CPU 4x + モバイル、公開の採点曲線で算出。
SI=0 の保守的下限でも 89)、CWV は FCP/LCP/CLS/TBT すべて good、一括ドシエ書き出し
**21倍**(2,167ms → 103ms、round 78)、WORDS 並べ替え **5倍**(round 79)。

**反問**: *速さは正しさとどう関係するか?* — **同じ行に同居する**。round 74 では応答性のための
yield が lost update を**到達可能に**し、round 78 では読み出し1回化が書き戻し窓を**同じ比率で
縮めた**。速度と正しさは独立ではない。

**判定: 長所**

### 1-5. 文書が自分を検算する

**実測**: DEPLOY STEP 7 の人手件数は表と突き合わせる(round 67。**初回実行で筆者の書き間違いを
検出**)、`npm run g10` の owner 向けリストは DEPLOY から**導出**(round 71。手書きの列挙が
既にずれていた)、旧プロジェクト名はリポジトリ全体を機械が見張る(round 66)。

**判定: 長所**

## 2. 短所

### 2-1. モノリス(ADR-0007)の代償が測定不能と迂回として残る

**事実**: 本体は `index.html` のインライン ES モジュールで vitest から import できない。
行カバレッジは**測定不能**(実測 0/0)、G10.02 は「モジュール網羅率」へ置換(round 44)。
テストは `from-source` ヘルパーで**関数本文を抜き出して評価**する迂回を要し、そのヘルパー自身に
盲点が2回あった(2-上記 1-3)。

**回避策**: モジュール網羅 21/21、実ソース評価、実ブラウザ spec。
**根治**: `lib/` 切り出し = **要ADR**(ADR-0007 の再検討)。

### 2-2. 「検査器に見えない性質」は構造的に残る

**事実**: 3回発生(round 66 / 77 / 83)。いずれも**コードは正しく、検査が性質を見ていなかった**。
round 83 に至っては、ソース不変条件テストが**上限を無力にしている当の形を要求**していた。

**回避策**: 旧実装で赤くなることの確認を習慣化。
**限界**: これは「見えていない」ことを探す作業なので、網羅の保証はない。**残る**。

### 2-3. 非 Chromium での機能差

**事実**: Vault は File System Access API 依存で Firefox / Safari に無い。
**round 87 で改善**(下記 3-1)したが、機能差そのものは残る。

### 2-4. 未裁決の設計判断

| 項目 | 状態 | 決定権者 |
|---|---|---|
| PBKDF2 300k vs OWASP 600k | ADR-0021 = Proposed。**実装すると既存の鍵が復号不能になり、正しいパスフレーズを「誤り」と表示する** | 要ADR(CLAUDE.md の human-in-the-loop 対象) |
| `/rss` のレート制限なし | 設計判断(任意フィード読取)。公開エンドポイントなので quota 消費は可能 | 要ADR |
| イベント間 `links[]` の永続化 | 導出部は round 33 で解決、永続化は未 | 要ADR(データモデル変更) |
| wrangler 依存の High 脆弱性 | 開発依存のみ。本番バンドルに含まれない | 要ADR |

### 2-5. G10.07 と STEP 8 は構造上 owner のみ

**事実**: G10.07 は (a) 自動検証 と (b) **主観評価 ≥ 4/5** の複合。(a) は充足
(1,803 tests / 181 browser specs)。(b) は**評価される側が自己採点しても情報量がゼロ**なので
代行しない — round 44 で「カバレジ ≥ 80%」を削除したのと同じ基準(満たしたことにするには
嘘をつくしかないゲートは、ゲートとして機能していない)。STEP 8 のタグ付けは STEP 7 通過**後**の
手順なので、順序として先に来ない。

**人手作業は round 67→70 で 12 シナリオ → 4 行に縮小済み**、しかも4行とも
「アプリのロジックではなく外側」(ベンダ応答 / OS 共有シート / インストール UI)の確認。

## 3. 改善点

### 3-1. Vault 非対応を**押す前に**伝える 【削る・機械 / round 87 で実施】

**問い**: 使えない機能を、使えないと分かる前に押させるのは正しいか。

**実測(改善前)**: Firefox / Safari では VAULT / SELECT VAULT / `v` キーが**押した後に**
エラーになる。判定は `ensureWriteAccess` の中にあった。

**最初の設計案とその却下**: 「ボタンを `disabled` + `title` で理由表示」を計画した。
**反問で却下**: *その `title` は影響を受ける当の利用者に見えるのか?* — **見えない**。
`title` はホバー前提で、**iOS Safari(影響ブラウザそのもの)では表示されない**。
「無効化 + 見えない理由」= **理由のない死んだボタン**で、押せばエラーが出る現状より**悪化**する。

**採用**: 伝える場所によって手段を変える。
- **Vault モーダル** … ボタンは `disabled`。理由は**同じモーダル内の本文テキスト**に出るので
  ホバーできない環境でも読める
- **カード詳細の VAULT** … **要素ごと出さない**。ここには理由を書ける本文が無い。
  機能の存在はヘッダ VAULT → モーダル本文で説明されるので発見経路は残る

### 3-2. 「検査器に見えない性質」を減らす 【疑う・機械】

**手**: 新しいテストを書くとき、**旧実装(または性質を壊した版)で赤くなることを必ず確認**する。
round 74 以降は実施済み。**未実施の既存テストが残っている**ので、順次確認するのが次の手。

### 3-3. `lib/` 切り出しの再評価 【簡素化・要ADR】

2-1 の根治。行カバレッジが測れるようになり、`from-source` ヘルパー(とその盲点)が**不要になる**
= 最良の部品は無い部品。ただし ADR-0007 の再検討が要る。

### 3-4. ADR-0021 の裁決 【疑う・owner】

「OWASP 準拠」は目的ではなく手段。**移行設計は既に書いてある**(後方互換)ので、決めるべきは
「いま移行するか」だけ。決めないこと自体が状態として残っている。

### 3-5. G10.07 の残り 【owner】

`DEPLOY.md` STEP 7 の4行(#3 / #7 / #8 / #9)+ 主観評価。所要は約5分。
`npm run g10` が現在の残件を**DEPLOY から導出して**表示する。

## 4. 総括

**この製品の強みは、主張が検査可能な形になっていること**である。ゼロ送信も、失敗時の挙動も、
性能も、「そう設計した」ではなく「そう測った」で裏付けられている。

**弱みは同じところから来る**。検査が性質を見ていなければ、緑は何も保証しない — それが3回
起きた。よって本書の判定も「テストが通っている」ではなく「**旧実装で赤くなることを確認した**」
を根拠にしている。

**残る作業は2種類しかない**。要ADR の設計判断(4件)と、owner にしかできない主観評価。
前者は決めれば進み、後者は代行すると**情報量がゼロになる**。どちらも「作業量」ではなく
「決定」であり、それが完成に最も近い状態の姿である。
