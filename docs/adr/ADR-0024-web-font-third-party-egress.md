# ADR-0024: Google Fonts への通信を続けるか(製品の一番の約束との緊張)

- **status**: Proposed(**未実装 / 人間の承認待ち**)
- **date**: 2026-08-25(round 91)
- **関連**: goal.md G0「個人データのサーバー送信ゼロ」/ `tests/browser-egress-allowlist.spec.mjs`
  (round 91)/ `docs/reviews/SOCRATIC-AUDIT.md` 1-1

## Context

`SOCRATIC-AUDIT` 1-1 は「ゼロ送信は**検査可能**」を長所として挙げていた。反問
*「その検査はどこにあるのか」* に対する答えは **どこにも無かった** — 個々の性質は測っていたが
(BYOK 未設定でベンダ通信ゼロ = round 69、Worker の SSRF = round 83)、
**通信を丸ごと記録して「これ以外は出ていない」と言う検査**は一つも無かった。

round 91 でそれを作った(`browser-egress-allowlist.spec.mjs`)。普通の一連の操作
(初回起動 → OPML取込 → POLL → 全ビュー巡回 → 検索 → メモ保存)で外部へ出たリクエストは
**4件 / 2オリジン**:

| オリジン | 何のため |
|---|---|
| `neus-proxy.example.workers.dev` | 利用者が設定した中継。**フィードURLのみ**を GET(本体なし、パラメータは `url` だけ)|
| **`fonts.googleapis.com`** | **Google Fonts のスタイルシート** |

利用者が入力したもの(メモ・検索語)は**一切出ていない**ことも同時に確認した。

**問題はここから**。製品の見出しの約束は「サーバーレス・端末内完結・**個人データのサーバー送信
ゼロ**」である。ところが**全ての起動で、全ての利用者について、無条件に** Google へ接続している。
送られるのは利用者の *content* ではないが、**IP アドレスと「この時刻にこのアプリを開いた」という
事実**が第三者へ渡る。しかも `docs/` にも `README.md` にも**この事実の記載は無い**。

## 測定(実 Chromium)

| 条件 | 描画 | CLS | FCP |
|---|---|---|---|
| フォント到達可能 | nav 9 要素・正常 | **0** | 124 ms |
| **フォント完全遮断** | nav 9 要素・正常 | **0** | **84 ms** |

- **遮断しても壊れない。** 構造は同一で、レイアウトシフトはどちらも **0**
  (`display=swap` と実在するフォールバックスタックのおかげで、既に良く作られている)。
- **むしろ速い。** 遮断時の方が FCP が短い(外部への DNS/TLS/リクエストが消えるため)。
- **失われるのは字形だけ。** これは計測できる欠陥ではなく**美的判断**であり、
  本 ADR が代われない部分である。

宣言されているスタックは:
```
--font-sans: "Noto Sans JP", -apple-system, BlinkMacSystemFont, system-ui, sans-serif;
--font-mono: "JetBrains Mono", ui-monospace, "SF Mono", monospace;
```
どちらも**実在するフォールバックを持つ**(飾りの空スタックではない)。

## 選択肢(3案比較)

### 案A: 現状維持

- **利点**: 見た目が変わらない。作業ゼロ。
- **欠点**: 見出しの約束と実際の挙動が食い違ったまま。しかも**その食い違いがどこにも
  書かれていない**。利用者が「端末内完結」を読んで期待するものと、実際に起きることが違う。
- **最低限やるべきこと**: この案を採るなら、**README に明記する**(「フォント配信のため
  Google へ接続します」)。**黙って続けるのが一番悪い。**

### 案B: フォントを自己ホストする

- **利点**: 字形が変わらず、第三者への接続が消える。約束と挙動が一致する。
- **欠点**: **CJK フォントは大きい。** Noto Sans JP を全字形で配ると配布物が桁で増える。
  サブセット化すればよいが、それは**ビルド工程の追加**であり、
  「単一 HTML + Worker + SW」という現在の配布形と、ゼロ依存・簡潔さの原則に反する。
  (具体的なファイルサイズは本環境から外部取得できず**未測定**。採用するなら実測が要る。)

### 案C: ウェブフォントをやめ、システムフォントに委ねる

- **利点**: 第三者接続が**ゼロ**になり、約束が字義どおり成り立つ。**FCP が改善**(実測)。
  削除なので部品が減る(最良の部品は無い部品)。CSP から2オリジン削れる。
- **欠点**: 環境によって字形が変わる。日本語の見え方は OS 依存になる。
  ブランドの一貫性は失われる。
- **実測の裏付け**: 遮断状態で**構造・CLS ともに劣化なし**。壊れるのは美観だけ。

## 推奨: **所有者の判断**(技術的には案C が最も筋が通る)

技術的な観点だけなら **案C** が明快である — 約束が字義どおり成り立ち、速くなり、部品が減る。
しかし**これはデザインの決定**であって、性能や正しさの決定ではない。字形が製品の同一性に
とってどれだけ重要かは、測っても出てこない。

**したがって本 ADR は案を選ばない。** ただし**一つだけ、選択肢に依らず言えること**がある:

> **黙って現状を続ける** のは3案のどれでもない。案A を選ぶなら README への明記が伴う。
> 約束と挙動が食い違うこと自体より、**食い違いが記録されていないこと**の方が問題である。

## 決定を要する点(人間の承認待ち)

1. **字形は、第三者接続ゼロと引き換えにする価値があるか。** 本 ADR の中心。
2. 案A を採る場合、README への明記を行うか(**推奨: 行う**)。
3. 案B を採る場合、CJK サブセット化のビルド工程を受け入れるか(ADR-0007 の簡潔さ方針と衝突)。

## 本 ADR では変更しない

- `index.html` のフォント読み込み(3案いずれも未採用のため)
- CSP の `style-src` / `font-src`(案C を採るときのみ削減できる)
- `browser-egress-allowlist.spec.mjs` の許可リスト — **現状を正しく記述している**。
  案C を採ればここから2行消え、それが変更の証跡になる。
