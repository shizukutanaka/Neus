# ADR-0023: `/rss` の流量制限をどう扱うか(G0「状態保持禁止」との緊張)

- **status**: Proposed(**未実装 / 人間の承認待ち**)
- **date**: 2026-08-25(round 90)
- **関連**: `_worker.js` / CLAUDE.md「Worker内での状態保持(KV / Durable Objects 使用は要ADR)」/
  `docs/reviews/SOCRATIC-AUDIT.md` 2-4

## Context

round 83 の Worker 監査で、SSRF・許可リスト・上限・タイムアウトはいずれも堅牢だと確認した。
残った未裁決事項が **`/rss` に流量制限が無い**ことである。`SOCRATIC-AUDIT` 2-4 は「要ADR」と
記録するに留めていたため、決定に必要な事実を測って本 ADR に集約する。

`/json` はホスト許可リスト(Wikipedia / Wikimedia / Qiita)で守られている。**`/rss` に許可リストが
無いのは設計判断**で、利用者が任意のフィードを購読できることが製品価値そのものだからである
(許可リスト化は機能を殺す。これは選択肢に含めない)。

結果として `/rss` は「**XML を返す任意の http(s) URL を中継する公開エンドポイント**」になる。

## 測定

### 正規利用の流量(実測: `index.html` の設定値より)

| 要素 | 値 |
|---|---|
| 自動同期の間隔(選択肢) | 1h / 6h / 12h / **24h**、既定 **6h** |
| 1 POLL のリクエスト数 | 登録ソース数(`for(const s of sources) fetchOne(s)`) |
| 単語収集の追加分 | 有効な単語 × 有効フィード(`WORD_FEEDS` は 8 種: news / reddit / hn / arxiv / qiita / zenn / hatena / github)|

典型例(ソース 10・単語 5・各単語 4 フィード・6h 間隔)は
`(10 + 20) × 4 = 120 リクエスト/日`。**1利用者あたり 1日 100〜200 の桁**であり、
現行の無料枠に対して余裕がある。

### 濫用時の流量

エンドポイントは公開・無認証・ホスト許可リスト無しなので、URL を知った第三者は
**自分のトラフィックを他人の Cloudflare 枠で中継できる**。制約は
`RSS_CONTENT_RE`(XML 系 Content-Type のみ)・5MB 上限・15秒タイムアウトのみで、
**回数の制約は無い**。被害は情報漏洩ではなく**所有者の枠の消費**(枠超過で正規利用者も止まる)。

### 現状の Worker の状態保持

`_worker.js` に KV / Durable Objects / `caches` / グローバル変数への書き込みは **0 箇所**
(機械確認済み)。G0「Worker は中継のみ・状態保持禁止」は現在**厳密に**成り立っている。

## 問題の核: 流量制限は本質的に状態を要する

「直近 N 秒に何回来たか」を知るには、その事実を**どこかに保持**しなければならない。
したがって本件は単なる機能追加ではなく、**G0 と正面から衝突しうる**。

**ただし G0 の意図を読み違えてはいけない。** CLAUDE.md の文言は
「**個人データのサーバ送信ゼロ** — Worker は中継のみ、状態保持禁止」であり、禁止の目的は
**利用者の個人データがサーバに残らないこと**である。IP 単位のカウンタは個人データに触れるか、
という問いには**触れうる**と答えるべきで(IP は状況により個人を識別しうる)、この点が
選択肢の評価軸になる。

## 選択肢(3案比較)

### 案A: 現状維持(流量制限を入れない)

- **利点**: G0 が厳密なまま。部品ゼロ。正規利用では実際に問題が出ていない。
- **欠点**: 濫用時に所有者の枠が消費され、**正規利用者も巻き添えで止まる**。検知手段も無い。
- **前提**: エンドポイント URL が広く知られないこと(=隠蔽に依存。防御ではない)。

### 案B: Cloudflare プラットフォーム側のレート制限ルール

- **要点**: 制限は**ダッシュボード設定**であり、`_worker.js` のコードは1行も変わらない。
  カウンタは Cloudflare のエッジが持ち、**我々のコードは状態を持たない**。
- **G0 との関係**: 「Worker は中継のみ・状態保持禁止」は**コードの性質として保たれる**。
  ただし「IP 単位の計数がプラットフォーム上で行われる」ことを G0 の趣旨に照らして
  許容するかは**所有者の判断**であり、本 ADR が代われない点である。
- **利点**: ゼロ依存原則に無傷(ライブラリ追加なし)。実装コストほぼゼロ。撤回も容易。
- **欠点**: 設定がリポジトリ外にあるため、**コードレビューで見えない**(`DEPLOY.md` に手順を
  書いても、実際の設定値との一致は機械検査できない)。プラン依存。

### 案C: Worker 内で KV / Durable Objects によるカウンタ

- **利点**: 設定がコードと同じ場所にあり、レビュー可能。細かい制御ができる。
- **欠点**: **G0 に正面から抵触**(CLAUDE.md が名指しで要 ADR としている当のもの)。
  IP をキーにすれば個人識別子を Worker が保持することになり、**製品の中核的主張を弱める**。
  KV の書き込みコストとレイテンシも増える。
- **判定**: 本 ADR は**推奨しない**。得られるものに対し、失うもの(不変条件の明快さ)が大きい。

## 推奨: **案B**、ただし条件付き

理由は3点:
1. **コードの不変条件を壊さない。** `_worker.js` は中継のみのまま保たれ、round 83 で確認した
   性質(SSRF・上限・タイムアウト)の説明も変わらない。
2. **可逆である。** 効果が無ければ設定を消せば元に戻る。案C は一度データモデルに入ると戻せない。
3. **問題の性質に合っている。** 守りたいのは「所有者の枠」であって利用者データではない。
   枠はプラットフォームの資源なので、プラットフォームの機構で守るのが素直である。

**条件(これを満たさないなら案A に留めるべき)**:
- `DEPLOY.md` に設定手順と設定値を明記し、**設定が存在しない状態を「未設定」として扱う**
  (「設定したつもり」を防ぐ。round 71 で `npm run g10` の手書きリストが既にずれていた前例がある)
- IP 単位の計数を G0 の趣旨に照らして許容する、という判断を**所有者が明示的に行う**

## 決定を要する点(人間の承認待ち)

1. **そもそも今やるか。** 正規利用では問題が出ていない。「起きていない問題を直さない」も
   十分に正当な決定である(その場合は案A を選び、本 ADR を Rejected として記録する)。
2. **案B の IP 計数を G0 の趣旨に照らして許容するか。** ここが本 ADR の中心で、
   技術的な最適解ではなく**製品の約束をどこまで厳密に読むか**の問題である。
3. **閾値。** 上の測定では正規利用は1利用者あたり 1日 100〜200 リクエスト。
   閾値を決めるなら、**正規利用の上限ではなく濫用の下限**から引くべきである。

## 本 ADR では変更しない

- `_worker.js`(案B はコード変更を伴わない。案C は不採用)
- `/rss` のホスト許可リスト化(機能を殺すため選択肢に含めない)
- 認証の導入(サーバーレス・端末内完結という前提と衝突する。別 ADR が要る)
