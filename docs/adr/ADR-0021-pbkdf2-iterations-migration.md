# ADR-0021: PBKDF2 反復回数の引き上げと移行方式

- **status**: Proposed(**未実装 / 人間の承認待ち**)
- **date**: 2026-08-16
- **round**: 40(第27次監査)
- **gate**: CLAUDE.md「重要分岐(Human-in-the-loop 必須)」の
  **マスターパスフレーズの暗号化方式変更**に該当。よって本 ADR は提案までとし、コードは変更しない。

## Context

`CONFIG.pbkdf2Iterations` は現在 **300,000**。BYOK の API キーを AES-GCM で暗号化する際の
鍵導出(PBKDF2-HMAC-SHA256)に使われる(`Crypto.deriveKey`)。

[OWASP Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)
の現行推奨は **PBKDF2-HMAC-SHA256 で 600,000 回**(2023 年時点の改定値。GPU 性能向上に伴い
推奨値は年々引き上げられており、それ以降さらに高い値も提案されている)。
つまり現状は推奨値のちょうど半分で、オフライン総当たり耐性が推奨の半分しかない。

### 現状の暗号実装で確認できた良い点(変更不要)

監査で以下は正しく実装されていることを確認した。本 ADR はこれらを変えない。

- IV は暗号化ごとに `crypto.getRandomValues` で新規生成(AES-GCM の IV 再利用なし)
- 導出鍵は `extractable=false`
- salt は 16 バイト乱数で永続化
- `decrypt` は失敗時に例外を投げ、呼び出し側は `catch{return null}` で **fail-closed**
  (部分的な鍵や空文字を下流のプロバイダへ送らない)

## 問題: 単純に数値を上げると既存データが復号不能になる

反復回数は**鍵導出の入力**なので、300,000 → 600,000 に変えると同じパスフレーズから
**別の鍵**が導出される。保存済み暗号文(BYOK API キー)は復号できなくなる。

さらに悪いことに、失敗の見え方が誤解を招く。`index.html` の unlock 処理は復号例外を
「パスフレーズが違います / wrong passphrase」と表示する。したがってユーザーには

> 正しいパスフレーズを入れているのに、永久に「パスフレーズが違います」と言われ続ける

という状態になり、原因究明が極めて困難。実害は「API キーの再入力が必要」に留まる
(他の個人データは平文で IndexedDB にあり影響なし)が、**沈黙の破壊**である点が問題。

## 検討した案

### 案A: 定数を書き換えるだけ(却下)
最小変更だが上記のとおり既存ユーザーの暗号文を壊し、しかも誤ったエラー文言で迷わせる。

### 案B: 暗号文にパラメータを埋め込む(推奨)
保存形式を「バージョン付き」に拡張し、**暗号文自体がどの反復回数で導出されたかを持つ**ようにする。

- 復号時: 埋め込まれた反復回数で鍵を導出 → 旧データはそのまま読める(後方互換)
- 暗号化時: 常に現行推奨値(600,000)を使う
- 結果として、ユーザーが次にキーを保存し直した時点で自動的に新パラメータへ移行する

形式案(現行は `base64(iv || ciphertext)`):

    v2: base64( 0x02 || iterations_be32 || iv(12) || ciphertext )
    v1: 先頭バイトが 0x02 でない既存データは、従来どおり iv(12)||ct として 300,000 で復号

先頭バイトによる版判別は、既存 v1 データの先頭が IV の乱数バイトであるため
`0x02` と衝突する確率が 1/256 ある。したがって**版判別は先頭バイトではなく
「設定キーを分ける」か「長さで判別」など衝突しない方法にすること**(実装時に要確定)。

### 案C: 起動時に一括再暗号化(却下)
セッションのパスフレーズが必要な時点でしか実行できず、暗黙の一括書き換えは
バックアップ整合性やロールバックの観点でリスクが高い。案B の遅延移行で十分。

## 決定(提案)

**案B を推奨**。ただし本項目は Human-in-the-loop ゲート対象のため、
**本 ADR の承認をもって初めて実装に着手する**。承認前に定数を書き換えてはならない。

## 承認時に必要な作業

1. 保存形式の版判別方式を確定(先頭バイト衝突を避ける)
2. `Crypto.encrypt` / `Crypto.decrypt` を版対応にする
3. 旧形式の復号パス(300,000)を保持する回帰テストを追加
4. `docs/FEATURE-AUDIT.md` と `SPEC.md` に記録
5. バックアップ/復元(`neus-backup-*.json`)との整合を確認 — 旧端末で作った
   バックアップを新版で復元しても API キーが読めること

## Consequences

- 承認・実装後: オフライン総当たり耐性が現行 OWASP 推奨に追いつく
- 後方互換が保たれ、既存ユーザーの API キー再入力は不要
- 暗号文が 5 バイト増える(無視できる)
- 未承認のまま放置した場合: 推奨値の半分のまま運用が続く(既知のリスクとして本 ADR に記録)
