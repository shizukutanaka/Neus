# ADR-0022: ソースアンカー方式(`expect(html).toContain(...)`)の位置づけを定める

- **status**: Proposed(**未実装 / 人間の承認待ち**)
- **date**: 2026-08-25
- **round**: 84(第71次監査)
- **gate**: 93ファイル・1,031アサーションに及ぶ**テスト方式そのものの変更**であり、
  CLAUDE.md「新機能追加 → ADR起票(影響大の場合)」および「ゼロ設計思考 — 慣性に抵抗、
  3案比較で選定」に該当する。よって本 ADR は**提案までとし、一括書き換えは行わない**。

## Context

本体ロジックは `index.html` のインライン ES モジュールにあり、vitest から `import` できない
(ADR-0007 のモノリス方針)。そのため本リポジトリの支配的なテスト様式は、**ソース文字列を
そのまま固定する**アンカーになっている。

```js
expect(html).toContain("const d=_wSortVal(a)-_wSortVal(b);return d!==0?d:...");
```

**実測した規模と内訳**(round 84 時点、`tests/*.{test,spec}.mjs` 全走査):

| 種別 | 件数 | 割合 | 例 |
|---|---:|---:|---|
| contract(セレクタ / i18n キー / 設定値) | 211 | 20% | `data-wact="rename"`, `'stats.storage'` |
| other short literal | 589 | 57% | `async function isPersisted(){` |
| **mechanism(書き方そのもの)** | **127** | **12%** | `db.onversionchange=()=>{`, `catch{` |
| long literal(どちらにせよ脆い) | 104 | 10% | 80文字超の実装行まるごと |
| **合計** | **1,031** | | 93ファイル |

## 問題: 測定された2つのコスト

### 1. 同期税 — 直近40コミット中 **18コミット(45%)** がアンカー更新を伴った

実装を正しく直すたびにテストが赤くなり、同一コミット内での同期が必要になる。本セッション中の
アンカー更新は round 42 / 55 / 56 / 59 / 66 / 69 / 72 / 74 / 75 / 76 / 79 / 80 / 82 / 83 で発生した。
**赤は欠陥ではなく、同じ事実を2箇所に書いていることの帳尻合わせ**である。

### 2. より重い問題: **誤った性質を固定しうる**(round 83 で実際に起きた)

`_worker.js` の `readCapped` は 5MB 上限を持つが、`arrayBuffer()` で**全部読み切ってから**
大きさを見ていた。実測では上限超過の本文でも上流から **40MB を丸ごと引いていた**
(逐次読みなら 5.1MB で打ち切れる)。Worker のメモリ上限は 128MB なので、十分大きな本文は
413 ではなく **isolate の死**になる。

このときテストは:

- describe 名 … `readCapped — streaming size enforcement`
- ソース不変条件 … `enforces streaming size even without Content-Length`
- 実際のアサーション4件 … **すべて返り値のみ**(返り値は新旧で同一)
- さらにアンカーが `const buf = await res.arrayBuffer()` を**要求していた**

つまり **「streaming」を名乗るテストが、streaming を不可能にする形を固定していた。**
アンカーは「実装が変わっていないこと」しか言えず、「実装が正しいこと」を言えない。

同型の見落としは本セッションで3回起きている(round 66 の古いミラー、round 77 の実行時合成
クラス名、round 83)。共通するのは**検査器に見えない性質**である。

## 選択肢(3案比較)

### 案A: 現状維持

- 利点: 変更ゼロ。モノリスのまま何かは検査できる。
- 欠点: 同期税 45% が続く。mechanism 系 127 件は**正しいリファクタを妨げ**、
  誤った性質を固定しうる。round 83 の再発を防ぐ手立てが無い。

### 案B: `lib/` へ切り出して本物の `import` にする

- 利点: 根治。アンカーが原理的に不要になる。行カバレッジも測れるようになる(G10.02 の限界も解消)。
- 欠点: **ADR-0007(単一ファイル配布 / ゼロビルド)の否定**にあたる。PWA の配布単位・CSP ハッシュ・
  Service Worker のキャッシュ戦略すべてに波及する。本 ADR の範囲を大きく超える。

### 案C(**推奨**): 用途で分け、mechanism 系だけを段階的に置換する

`tests/helpers/from-source.mjs`(round 60 導入、現在6ファイルで使用)は既に**実物の関数を
取り出して評価**できる。これを既定の道具とし、アンカーは役割を限定する。

| アンカーの種別 | 方針 |
|---|---|
| contract(211件) | **残す。** セレクタ・i18n キー・設定値は「文字列であること」自体が契約 |
| mechanism(127件) | **置換対象。** 実ソース評価による**性質のテスト**へ移す |
| long literal(104件) | 置換対象。性質へ移せないものは短い contract へ縮める |
| other(589件) | 現状維持。移行の必要が生じた箇所から順次 |

- 利点: ADR-0007 を触らない。効果の大きい 12% に絞れる。既存の道具で足り、新規依存ゼロ。
  移行はファイル単位で独立しており、途中で止めても壊れない。
- 欠点: 二方式の併存が続く。どちらを使うべきかの判断が必要になる(上表がその判断基準)。

## 決定を要する点(人間の承認待ち)

1. 案C を採るか。
2. 採る場合、mechanism 系 127 件の移行を**どの粒度で**行うか
   (ファイル単位で分割するか、監査ラウンドのついでに触れた分だけ直すか)。
3. `from-source.mjs` の限界(依存注入が必要・DOM/IDB に触る関数は不可)を踏まえ、
   移行できない箇所をどう扱うか。

## 本 ADR では変更しない

一括書き換えは行わない。1,031 件のうち 8 割は現に機能しており、方式変更は**採否そのものが
設計判断**だからである。round 83 で実際に誤りを固定していた1件は、その round 内で
**性質を名指しする形へ書き直し済み**(`getReader()` を使う / 超過時に `cancel()` する)。
